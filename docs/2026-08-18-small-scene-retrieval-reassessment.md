# 小规模场景知识检索独立复核

> 状态：非规范性复核报告
> 日期：2026-08-18
> 范围：仅重新判断当前两个业务场景是否需要检索、Embedding 和专用向量数据库。本文不修改现有规范设计，也不表示代码已经实现；如结论被接受，应另行修订正式技术设计。

## 1. 结论

当前场景的唯一推荐是：

> **离线读取场景全部资料，生成并由人工确认“产品与服务知识卡 + FAQ”；通话时优先直接使用知识卡/FAQ，长尾问题再使用 PostgreSQL 词法检索；当前不生成 Embedding，也不部署 Qdrant。**

三件事必须分开判断：

| 问题 | 当前结论 |
| --- | --- |
| 是否需要检索 | 场景 1 的长尾问答需要；场景 2 的全量总结不需要 Top K 检索 |
| 是否需要 Embedding | 当前没有证据证明需要；先以真实问题集比较词法与向量召回 |
| 是否需要专用向量数据库 | 当前不需要；即使后续需要 Embedding，也先用 PostgreSQL `pgvector` 精确检索 |

RAG 原始论文使用的是“生成模型 + 可检索外部记忆”，其具体实现用了大规模 Wikipedia dense index；这证明 dense retrieval 可用于知识密集任务，不代表任何小知识库都必须使用向量检索。[Lewis 等，RAG](https://arxiv.org/abs/2005.11401)

## 2. 场景 2：一键提取“核心产品、服务亮点”

这个任务的目标是**覆盖完整资料并进行结构化归纳**，不是根据一个问题找最相似的几段。因此不应先用向量 Top K 截断资料：通用查询“核心产品、服务亮点”可能漏掉文档中低频但重要的限制、适用范围或差异化卖点。

推荐流程：

1. 读取当前场景关联的全部 READY 版本正文；
2. 在单次输入可控时一次性抽取产品、适用客户、核心能力、服务亮点、限制和来源；
3. 超出安全输入量时按文档/章节分批抽取，再合并、去重并标记冲突；
4. 展示原文件、页码或时间点，由用户确认后写入提示词版本。

单次全量输入的工程门槛为：资料、指令和预留输出合计不超过所选模型最大输入的 **50%**；超过后使用分批归并，而不是向量 Top K。50% 是本项目的保守起始门槛，不是模型厂商保证。即使长文本在上下文窗口内，模型使用中部信息的能力仍可能下降；`Lost in the Middle` 在多文档问答中观察到了明显的位置偏差。[Liu 等，Lost in the Middle](https://arxiv.org/abs/2307.03172)

所以场景 2 需要文档解析、结构化抽取、来源和人工确认，但**不需要 Embedding 或向量数据库**。

## 3. 场景 1：通话中回答产品问题

### 3.1 分级处理

| 客户问题 | 处理方式 | 是否检索 |
| --- | --- | --- |
| 问候、确认听见、流程推进 | 提示词和当前对话 | 否 |
| 产品定位、核心能力、主要亮点 | 已确认的产品与服务知识卡 | 否 |
| 已整理的高频问题 | FAQ 精确/近似匹配后直接取答案与来源 | 轻量查找 |
| 价格、参数、政策、交付周期、案例等长尾事实 | 在当前任务冻结的场景版本内检索切片 | 是 |
| 无命中或资料冲突 | 明确“不确定/需要确认”，不得编造 | 是，但返回 no-hit/conflict |

知识卡建议控制在约 **2,000 tokens** 内并随任务版本冻结。它不是原文替代品：未被知识卡和 FAQ 覆盖的事实才查询原始切片。这样避免每轮重复塞入全部文档，也降低长上下文中无关内容干扰。

### 3.2 当前检索方式

当前推荐 PostgreSQL 词法检索：

- 产品名、型号、金额、单位和专有名词使用精确词/短语匹配；
- 正文切片使用 PostgreSQL Full Text Search 排名；
- 拼写误差、近似产品名和部分词使用 `pg_trgm`；
- 对“续费/续约”等已知业务说法维护小型场景同义词表；
- 始终按 `tenant_id + frozen_version_ids` 限定范围，并返回来源。

PostgreSQL 原生支持 `tsvector/tsquery`、`ts_rank/ts_rank_cd` 和 GIN 全文索引；`pg_trgm` 支持文本相似度，以及带索引的 `LIKE/ILIKE`、正则和近似匹配。[PostgreSQL 全文检索](https://www.postgresql.org/docs/current/textsearch-tables.html)、[排名函数](https://www.postgresql.org/docs/current/textsearch-controls.html#TEXTSEARCH-RANKING)、[`pg_trgm`](https://www.postgresql.org/docs/current/pgtrgm.html)

注意：PostgreSQL 的 `ts_rank/ts_rank_cd` 不是 BM25，设计和代码中应称为“词法检索”。中文分词效果必须用 `ts_debug` 和真实资料验证；若分词不可靠，保留精确短语与 `pg_trgm` 作为基线，不能假设换一个索引名称就会获得语义理解。[PostgreSQL `ts_debug`](https://www.postgresql.org/docs/current/textsearch-debugging.html)

Embedding 的价值是召回“含义相近但几乎没有共同词”的问题。DPR 论文在开放域问答中证明 dense retrieval 可以明显超过 BM25；但 BEIR 的跨领域评测同时表明 BM25 是稳健基线，dense 模型并非在所有域都更好。因此必须在本项目资料和客户问法上评测，而不能仅凭通用榜单选择。[DPR](https://arxiv.org/abs/2004.04906)、[BEIR](https://arxiv.org/abs/2104.08663)

## 4. 方案比较

| 方案 | 当前适用性 | 结论 |
| --- | --- | --- |
| 通话每轮注入全部文档 | 文档极短时可做对照，但重复消耗 tokens、增加时延且有长上下文位置风险 | 不作为默认方案 |
| 离线全量生成知识卡/FAQ | 同时服务总结和高频通话问题，内容可审核、可冻结 | 必做 |
| PostgreSQL 词法检索 | 小场景、专有名词、数字、政策和参数匹配直接，系统最少 | 当前默认 |
| Embedding 线性扫描 | 可快速验证语义召回，但应用内缓存、多实例一致性和持久化不适合作为长期实现 | 仅评测 |
| PostgreSQL `pgvector` | 默认精确近邻搜索、perfect recall；可按租户/版本过滤并与业务数据共用事务和备份 | 需要 Embedding 时首选 |
| Qdrant | 擅长独立向量服务、过滤 HNSW、分片和水平扩展，但增加网络、鉴权、监控、备份和高可用系统 | 当前不需要 |

`pgvector` 默认执行精确最近邻搜索；HNSW/IVFFlat 是以召回率换速度的近似索引。[pgvector 官方 README](https://github.com/pgvector/pgvector#querying)

Qdrant 自身也会在候选向量较小时优先 full scan，而不是 HNSW；其默认 `full_scan_threshold` 是 10,000 KB。Qdrant 的生产部署还需要独立安全、分片、复制和恢复能力；官方文档指出自托管实例默认对所有接口开放且无认证，而最小容错集群需要三个节点和至少两副本。[Qdrant 索引配置](https://qdrant.tech/documentation/manage-data/indexing/)、[生产检查清单](https://qdrant.tech/documentation/production-checklist/)、[扩缩容与容错](https://qdrant.tech/documentation/scaling/)

因此，对“每个场景几份文档”的过滤后候选集，Qdrant 的核心规模优势尚不存在，额外服务反而扩大运维和故障面。

## 5. 适用门槛与升级顺序

以下是需要通过压测校正的项目起始门槛，不是数据库厂商的硬上限：

1. **直接使用知识卡/FAQ**：卡片不超过约 2,000 tokens，且评测问题已有明确答案。
2. **PostgreSQL 词法检索**：每场景不超过 10 份文档或 5,000 个切片、峰值知识查询不超过 20 QPS，并满足检索 P95 ≤ 100 ms。
3. **增加 Embedding**：词法方案在真实问题集上 `Recall@5 < 95%`，或“无共同词改写”子集 `< 90%`；同时 Embedding 精确检索至少提升 5 个百分点。
4. **增加 `pgvector`**：第 3 条成立时，在 PostgreSQL 保存向量并先做场景过滤后的精确扫描；只有压测要求时再增加 HNSW。
5. **评估 Qdrant**：只有在 `pgvector` 经索引和查询优化后，仍无法满足峰值并发/时延，或活跃向量达到百万级且确有独立扩缩容、跨业务共享检索服务的需求时才评估。不能仅因为“使用了 Embedding”就部署 Qdrant。

## 6. 可验证评测集

从真实场景资料建立至少 **120 条**人工标注问题，每条记录是否应检索、标准答案、必须命中的来源和允许的同义表述：

- 25 条产品名、能力和直接表述；
- 25 条同义改写，尽量减少与原文共同词；
- 20 条价格、数字、政策、日期和交付周期；
- 15 条跨章节或跨文档问题；
- 15 条资料中没有答案的问题；
- 10 条冲突或过期版本问题；
- 10 条问候、确认和流程话术。

同一数据集依次评测“知识卡/FAQ”“知识卡 + 词法检索”“知识卡 + Embedding 精确检索”，不得为不同方案换题。最低验收：

- 可回答问题证据 `Recall@5 ≥ 95%`；改写子集 `≥ 90%`；
- 数字、价格和政策问题的最终答案正确率 `100%`；
- 跨租户、跨场景、非冻结版本命中数 `0`；
- 无答案问题编造率 `0`，应返回 no-hit；
- 检索 P95 `≤ 100 ms`，通话端到端时延另行按语音链路验收；
- 一键总结的每个关键结论都有来源，冲突信息不被静默合并。

只有评测证据达到升级条件，才增加下一层技术。否则维持“知识卡/FAQ + PostgreSQL 词法检索”的最小闭环。
